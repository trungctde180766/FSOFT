      🧠 Kiến Trúc Bộ Nhớ JVM & Cơ Chế Thu Gom Rác (Garbage Collection)

      Stack Memory vs Heap Memory
      • Stack (Mỗi Thread 1 Stack riêng): Lưu trữ Stack Frame chứa các biến nguyên thủy cục bộ (primitive local variables) và con trỏ tham chiếu (reference pointer) tới Heap. Quản lý LIFO tự động thu hồi khi method return. Không cần GC. Tràn bộ nhớ: StackOverflowError (thường do đệ quy vô hạn).
      • Heap (Chia sẻ chung cho toàn bộ JVM): Nơi cấp phát tất cả Object và Mảng (Arrays). Được dọn dẹp bởi Garbage Collector (GC). Tràn bộ nhớ: OutOfMemoryError: Java heap space.
      Phân Vùng Heap & Thế Hệ Đối Tượng
      • Young Generation: Gồm Eden Space và 2 Survivor Spaces (S0, S1). Đối tượng mới sinh ra nằm ở Eden. Minor GC dọn dẹp liên tục, copy object sống sót qua lại giữa S0 và S1.
      • Old Generation (Tenured): Chứa các object sống sót qua số chu kỳ nhất định (mặc định MaxTenuringThreshold = 15). Khi Old Gen đầy sẽ kích hoạt Major GC / Full GC (gây Stop-The-World).
      • Metaspace (từ Java 8 thay thế PermGen): Lưu Class metadata, bytecode, static fields. Nằm trên bộ nhớ Native OS thay vì Heap, co giãn tự động theo RAM máy chủ.
      String Constant Pool & Hàm .intern()

      String s1 = "Java"; tạo đối tượng trong String Constant Pool (nằm trong Heap từ Java 7+). String s2 = new String("Java"); bắt buộc tạo 1 object mới toanh ngoài Heap thông thường. Khi gọi s2.intern(), JVM sẽ tìm xem chuỗi "Java" đã có trong Pool chưa: nếu có, trả về tham chiếu từ Pool; nếu chưa, thêm vào Pool. Do đó s1 == s2.intern() trả về true!

      🧩 4 Quy Tắc Sắt Về Ghi Đè Phương Thức (Method Overriding)

      Thành phần Quy tắc lớp con (Child Class) Lỗi vi phạm thường gặp
      Access Modifier Phải rộng hơn hoặc bằng lớp cha: public > protected > default > private Cha là protected, con ghi đè là default $\to$ Compile Error: "cannot reduce visibility".
      Return Type Phải cùng kiểu hoặc là kiểu dẫn xuất con (Covariant Return Type từ Java 5). Cha trả về Number, con trả về Integer (HỢP LỆ). Nhưng cha trả về void, con trả về int $\to$ Lỗi.
      Checked Exceptions Chỉ được throws cùng loại hoặc là Exception con, hoặc không throws gì cả. Cha throws IOException, con throws Exception $\to$ Compile Error (không được ném checked exception rộng hơn cha).
      static / final / private final không cho override. static không thể override (chỉ là Method Hiding). private không kế thừa. Gọi static method qua object reference Parent p = new Child(); p.staticMethod(); $\to$ vẫn chạy hàm của Parent!

      📦 Bản Chất Cơ Chế Hoạt Động Của HashMap & Hợp Đồng HashCode / Equals

      Cấu Trúc Node & Công Thức Tính Vị Trí Bucket

      Bản chất HashMap là một mảng các Node: Node<K,V>[] table. Khi gọi put(key, value):
      1. Tính hash từ key: h = key.hashCode() ^ (h >>> 16) (phép XOR dịch phải 16 bit giúp tán đều bit cao xuống bit thấp, chống đụng độ).
      2. Tính index mảng: index = (n - 1) & hash (trong đó $n$ là dung lượng mảng, luôn là lũy thừa của 2: 16, 32, 64...). Phép bitwise AND này tương đương với hash % n nhưng chạy ở tốc độ vi xử lý phần cứng.

      Xử Lý Xung Đột (Collision Resolution) & Cây Đỏ Đen (Java 8+)

      Nếu 2 key khác nhau rơi vào cùng một index (xung đột hash), chúng được nối tiếp dưới dạng LinkedList (Separate Chaining). Từ Java 8:
      • Khi 1 bucket có $\ge 8$ phần tử và tổng dung lượng bảng $\ge 64$, danh sách liên kết sẽ tự động chuyển hóa thành Red-Black Tree (Cây Đỏ Đen), giảm độ phức tạp tìm kiếm từ $O(n)$ xuống còn $O(\log n)$.
      • Khi số phần tử trong bucket giảm xuống $\le 6$, cây sẽ thoái hóa ngược lại thành LinkedList (Untreeify).

      Hợp Đồng Bất Di Bất Dịch: equals() và hashCode()

      Nếu 2 object a.equals(b) == true $\implies$ a.hashCode() == b.hashCode() BẮT BUỘC phải bằng nhau! Ngược lại, 2 object có cùng hashCode thì CHƯA CHẮC đã equals (đây chính là va chạm hash). Nếu bạn override equals mà quên override hashCode, bạn sẽ làm hỏng hoàn toàn HashSet và HashMap vì chúng không thể tìm thấy phần tử dù dữ liệu giống hệt nhau!

      🗄️ SQL Indexing B+Tree & 4 Cấp Độ Cô Lập Giao Dịch (Transaction Isolation)

      Isolation Level Dirty Read Non-Repeatable Read Phantom Read Đặc điểm & Ghi chú
      Read Uncommitted BỊ (Đọc dữ liệu rác chưa commit) BỊ BỊ Cấp thấp nhất, gần như không dùng trong thực tế.
      Read Committed KHÔNG BỊ (Đọc lại thấy dữ liệu đã UPDATE) BỊ (Thấy dòng mới INSERT) Mặc định của Oracle, SQL Server, PostgreSQL.

      B+Tree Index: Clustered vs Non-Clustered

      • Clustered Index (Chỉ mục cụm): Các nút lá (Leaf nodes) chứa trực tiếp toàn bộ dòng dữ liệu thực tế (Physical Data). Mỗi bảng chỉ có duy nhất 1 Clustered Index (thường là Primary Key).
      • Non-Clustered Index (Chỉ mục thứ cấp): Các nút lá chỉ chứa giá trị của cột được đánh index và con trỏ trỏ tới Clustered Key tương ứng. Nếu câu query chọn các cột không nằm trong index, DB phải làm thao tác Bookmark Lookup (Key Lookup) về Clustered Index để lấy nốt dữ liệu.

      🍃 Vòng Đời Spring Bean & 2 Cái Bẫy Sát Thủ Của @Transactional

      Chu Kỳ Vòng Đời Của Spring Bean
      1. Khởi tạo Instance (Constructor invocation).
      2. Inject dependencies (Setter / Field Injection qua @Autowired).
      3. Gọi các Aware Interfaces (BeanNameAware, BeanFactoryAware, ApplicationContextAware).
      4. BeanPostProcessor.postProcessBeforeInitialization()
      5. Khởi tạo nội bộ: @PostConstruct $\to$ InitializingBean.afterPropertiesSet() $\to$ custom init-method.
      6. BeanPostProcessor.postProcessAfterInitialization() (Tạo CGLIB/JDK Dynamic Proxies cho AOP, Transaction, Security).
      7. Sẵn sàng phục vụ (Bean in Ready state).
      8. Hủy: @PreDestroy $\to$ DisposableBean.destroy() $\to$ custom destroy-method.
      2 Bẫy Chết Người Với @Transactional

      Bẫy 1 - Self-Invocation (Gọi nội bộ trong cùng Class): Spring Transaction hoạt động dựa trên Proxy pattern bọc ngoài Bean. Nếu hàm A (không có @Transactional) gọi trực tiếp hàm B (có @Transactional) trong cùng class qua this.methodB(), cuộc gọi sẽ không đi qua Spring Proxy $\implies$ Transaction KHÔNG ĐƯỢC KÍCH HOẠT!

      Bẫy 2 - Default Rollback Rule: Mặc định Spring Transaction chỉ rollback với Unchecked Exception (con của RuntimeException hoặc Error). Nếu phương thức ném ra Checked Exception (như IOException, SQLException, Exception), Spring mặc định COMMIT GIAO DỊCH! Muốn an toàn bắt buộc phải ghi: @Transactional(rollbackFor = Exception.class).

      📜 10 Điều Răn Clean Code & Comment Code FSOFT (Trích Dataset Fresher v2.0)

      1. Đặt tên phương thức có ý nghĩa (Self-explanatory): Luôn bắt đầu bằng động từ, theo chuẩn camelCase, ví dụ: calculateOvertimePay(), findActiveUsersByDepartment() thay vì doCalc() hay data().
      2. Không bao giờ nuốt ngoại lệ (Do not swallow exceptions): Tuyệt đối cấm viết catch(Exception e) {} rỗng. Phải log ít nhất ở mức WARN/ERROR kèm stack trace hoặc bọc ném ra Custom Business Exception.
      3. Luôn giải phóng tài nguyên qua try-with-resources: Mọi đối tượng mở I/O (Connection, Statement, ResultSet, InputStream, Scanner) phải dùng try(...) để JVM tự động gọi close(), triệt tiêu rò rỉ bộ nhớ (Connection leak).
      4. Trục xuất Magic Numbers & Magic Strings: Mọi giá trị hằng số dùng trong kiểm tra nghiệp vụ phải được khai báo dạng public static final int MAX_LOGIN_ATTEMPTS = 5; hoặc enum.
      5. Tuân thủ định dạng Javadoc: Mọi class và public method phải có Javadoc mô tả mục đích, tham số @param, giá trị trả về @return và ngoại lệ có thể ném @throws.
      6. Tránh lồng ghép If-Else quá sâu (Arrow Anti-pattern): Áp dụng kỹ thuật Guard Clauses (Kiểm tra điều kiện lỗi và return sớm ngay đầu hàm) để giữ code thẳng và phẳng.
      7. Ưu tiên Composition hơn Inheritance: Chỉ kế thừa khi thực sự có quan hệ "IS-A" chặt chẽ; ngược lại hãy dùng "HAS-A" (DI) để hệ thống linh hoạt và dễ unit test.
      8. Tránh trả về null cho Collections: Luôn trả về Collections.emptyList() thay vì null để người gọi không bị dính NullPointerException.
      9. Immutability cho DTO & Entity Keys: Khai báo các field không đổi dạng final, cân nhắc sử dụng Java Record (Java 14+) hoặc Lombok @Value để đảm bảo an toàn đa luồng.
      10. Mỗi phương thức chỉ làm đúng một việc (SRP): Độ dài phương thức lý tưởng dưới 25 dòng code; nếu vượt quá hãy tách thành các private helper methods có tên tường minh.
